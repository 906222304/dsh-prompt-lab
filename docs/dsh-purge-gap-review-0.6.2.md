## 最值得借鉴的三件事

### 1. 项目指令文件发现与选择：减少复制粘贴，优先做

**上游已实现：** 从当前目录向项目根查找 `AGENTS.md`、`CLAUDE.md` 及两种 `.local.md`，显示路径、层级、修改时间、大小与预览；只拼接用户选中的、仍属于当前目录候选集的文件。没有找到版本库根时只看当前目录，不递归扫描整个磁盘。

证据：[目录链与扫描](https://github.com/HunYiSage/dsh-purge/blob/40c9bc6c7b5dfdc400b14900fba2ac706b683657/lib/rules.js#L396)、[所选文件拼接](https://github.com/HunYiSage/dsh-purge/blob/40c9bc6c7b5dfdc400b14900fba2ac706b683657/lib/rules.js#L538)。

**我们的缺口：** 已有“粘贴规范→AI 提取规则”，没有方便的项目文件来源入口。

**建议实现：** 在现有 AI 创作材料区增加“从项目规范选择”。优先复用宿主已有的指令文件清单；宿主没有可靠接口时，提供显式项目目录选择与有限扫描。展示文件来源、适用目录和内容摘要，选中后冻结路径、内容与哈希，再进入已有提取/整理候选流程。

不要原样复制上游“将规则写回 AGENTS.md/CLAUDE.md”的激活方式。Prompt Lab 首版只导入为候选资产，避免改写项目文件；也不要把宿主本来就加载的同一段原文再次注入。

**验收重点：** 多层项目规则顺序清楚；无根目录时只读取当前目录候选；解析真实路径后不越过选择的项目边界；文件修改后提示重新预览；超限文件明确拒绝；取消不写资产；宿主加载情况无法核实时显示“未知”，不声称已完成去重。

### 2. 分层诊断与来源追踪：让“有没有生效”可判断，优先做

**上游已实现：** 状态接口区分 ready、宿主支持情况、补丁 applied/pending/skipped/drifted 等状态，而不是只给一个总开关。

证据：[分层状态接口](https://github.com/HunYiSage/dsh-purge/blob/40c9bc6c7b5dfdc400b14900fba2ac706b683657/lib/index.js#L2029)。这证明的是上游对自身改造状态的展示，并不证明它已实现我们需要的逐请求注入追踪。

**我们已有的基础：** `lib/state.js:303` 记录真实求值，`:368` 捕获组装。后者明确标记 `scope: process`，并注明“可能仍有后续处理，不等于模型 API 最终请求”。因此不是从零做诊断，而是补关联和解释。

**建议实现：** 沿用设置中折叠的诊断区域，按以下层次显示：

1. 已保存：资产及配置版本。
2. 已注册：补充段名称与顺序。
3. 已求值：时间、规则来源、正文摘要哈希、排除原因。
4. 已观察到组装：对应配置版本及是否过期。
5. 当前请求参与情况：只有拿到可靠的 session/request 关联证据才展示；缺少接口时明确显示“未取得请求证据”。

并检测可见组装中与其他插件或项目文件的重复内容：精确重复可确认，语义近似只提示可能重复。被截断的快照不能用来证明“不重复”；其他插件的注册名称也不能单独证明它重复注入。

**验收重点：** 保存后尚未发消息，不误报“当前请求已使用”；跨会话组装不串成当前会话；禁用、空正文、停用规则、旧快照分别解释；只凭文本观察不能断言模型拒绝、网关拦截或工具权限失败的根因。完整上下文浏览继续交给 dsh-context。

### 3. 证据分级与失败复现：借鉴思想，接入现有测试集

**上游已实现：** 红队证据账本区分 claimed（口头声称）、observed（观察证据）、derived（推导）、inferred（推测）；报告复现模块要求将合成内容标记为 synthesized，资料不足时不编造重放材料。

证据：[证据账本](https://github.com/HunYiSage/dsh-purge/blob/40c9bc6c7b5dfdc400b14900fba2ac706b683657/lib/redteam/evidence-ledger.mjs#L1)、[报告复现约束](https://github.com/HunYiSage/dsh-purge/blob/40c9bc6c7b5dfdc400b14900fba2ac706b683657/lib/redteam/report-replay.js#L1)。

**我们的缺口：** 当前已有“选定对话→提取长期规则”和独立测试集，但没有顺畅的“这次失败→回归样例”入口。`normalizeSuite` 目前也不保留逐条会话来源及失败输出，因此需要扩展存储格式，不能只加按钮。

**建议实现（产品延伸，不是上游现成功能照搬）：** 用户选定一次失败的输入、输出和纠正意见，点击“加入回归集”；AI 起草可编辑的参考资料、评分标准或检查项。保存来源 sessionId/seq/消息哈希、失败输出、证据类型及人工确认记录。确认后的样例再接现有 A/B 和优化流程。

历史失败默认进入训练/回归材料。为本次失败专门改过提示词后，再用同一个失败样例通过，不能当作独立验证；需要保留不同的验证样例。模型自述“成功调用工具”也不能当作实际工具执行通过。

**验收重点：** 不采集未选消息；来源可回看；人能修改标准；没有标准不能通过；更换输入不会沿用旧证据；现有文本试跑不伪装成 Agent 端到端验收。无需引入整个红队 SQLite 平台。

## 不建议照搬的部分

- 宿主包补丁、启动 shim、自动重应用和重启链路：宿主版本耦合强，超出当前提示词资产工作台的职责。
- 审批/沙箱绕过及无条件自动继续：不作为提示词工程能力引入。
- 整套红队业务工具、数据库和技能：可以借证据与复现方法，不需要把产品变成另一套红队平台。
- 万能“破甲”长提示词：模型、渠道和任务的效果必须分别验证，不能用宣传描述替代测试结论。
- 只看配置字段就认定已实现的功能。例如固定版本中 `injectOnce` 出现在默认值及布尔字段清单，但 `injectAllowedNow()` 只判断 enabled；在所查 lib 源码中没有找到该字段的会话级消费逻辑。不能直接把它列为可迁移的“一次注入”实现。

来源：[注入开关实际判断](https://github.com/HunYiSage/dsh-purge/blob/40c9bc6c7b5dfdc400b14900fba2ac706b683657/lib/index.js#L212)。

如后续直接复用上游代码，应保留其 Apache-2.0 许可证、NOTICE 和相关署名要求；单纯借鉴设计与直接复制实现应在变更记录中区分。

## 推荐推进顺序

1. 先做“项目规范选择→现有 AI 提取/整理”与注入诊断补强。这两项直接减少手工输入、解释当前行为，基本复用现有界面。
2. 再做“失败对话→回归样例”，补逐样例来源结构及训练/验证约束，接已有试跑和优化。
3. 最后做真正的项目/会话绑定及场景方案；需要先验证宿主契约，并用并行两个会话、切换项目、热加载和版本更新检验隔离。

本次交付是借鉴评审文档；运行代码、版本号和正在运行的插件均未修改。
